# GitHub Star Category Policy

## Ranking Signals

Classify by what the repository helps the user do:

1. README/description and product purpose
2. repository topics
3. name
4. implementation language as a tiebreaker only

A Rust-written bundler belongs in Build & DX; a Swift productivity utility belongs in CLI & Tools.

## List Design

- Preserve populated existing lists when their meaning is clear.
- Prefer 15-25 lists for a large account and never exceed GitHub's 32-list limit.
- Consider splitting a list above roughly 40 repositories by sub-purpose.
- Merge tiny overlapping categories instead of creating a list for each framework or language.
- In selective mode, create a new list only when existing lists clearly do not fit.

## Starting Taxonomy

Use only categories supported by the actual stars:

- AI & Agents
- Frontend Frameworks
- Mobile
- Backend & Data
- Build & DX
- CLI & Productivity
- UI & Design
- Network & Proxy
- DevOps & Infrastructure
- Low-Code & CMS
- Learning & Curated Lists
- Miscellaneous

Framework-specific lists such as React or Vue are justified only when the account has enough repositories to make them useful.

## Proposal Table

For each repository show:

| Repository | Purpose | Existing lists | Proposed lists | Reason |
| ---------- | ------- | -------------- | -------------- | ------ |

Separately list every proposed new list with its description. Do not hide removals or replacements inside a general summary.
